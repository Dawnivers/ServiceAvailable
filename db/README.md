# db/ —— 数据库脚本

D16 格网热力图相关的 SQL，按编号顺序执行。

| 文件 | 做什么 | 何时跑 | 耗时 |
|---|---|---|---|
| `01_ddl_grid_500m.sql` | 建表 `grid_500m`（15 列 + 2 个 GIST 索引） | 一次 | < 1 s |
| `02_build_grid_500m.sql` | 生成 500 m 格网（39,820 格） | 一次；`admin_area` 变化时重建 | ~1 min |
| `03_refresh_grid_500m.sql` | **全量**重算全部统计列 | 删除/改坐标/整表重灌之后 | 5–15 min |
| `03b_refresh_incremental.sql` | **增量**：只重算新增 POI 影响的约 10 格 | **只新增 POI 时** | **< 1 s** |
| `04_verify_grid_500m.sql` | 验收（只读，不修改数据） | 每次刷新后 | ~1 min |

```powershell
$env:PGPASSWORD='<密码>'
$psql = "D:\PostgreSQL18.4\data\18\bin\psql.exe"
& $psql -h localhost -p 5432 -U postgres -d Spatial -f 01_ddl_grid_500m.sql
& $psql -h localhost -p 5432 -U postgres -d Spatial -f 02_build_grid_500m.sql
& $psql -h localhost -p 5432 -U postgres -d Spatial -f 03_refresh_grid_500m.sql
& $psql -h localhost -p 5432 -U postgres -d Spatial -f 04_verify_grid_500m.sql
```

> ⚠️ 直接 `psql -c "含中文的 SQL"` 会报 `无效的 "UTF8" 编码字节顺序`
> （PowerShell 用 GBK 送出，psql 按 UTF8 解析）。
> **用 `-f` 读文件不受影响**，实测通过；或先 `chcp 65001`。

## 新增 POI 后怎么刷新

**只新增**（最常见）→ 跑 `03b`，**不到 1 秒**：

```powershell
& $psql -h localhost -p 5432 -U postgres -d Spatial -f 03b_refresh_incremental.sql
```

工作原理：`grid_500m_refresh_state` 表记住「已经完整反映到哪条 POI」（`last_max_gid`）。
`gid` 是 serial 序列、单调递增，所以 `gid > last_max_gid` 精确等于「本次新增」。
每条新 POI 平均影响 **9.34 个格子**，只重算这些格；最后全表重算 5 个倍数列（纯算术，1–2 秒，
因为新增 POI 会改变分母，所有倍数都该跟着变）。

**必须跑全量 `03` 的情况**：

| 情况 | 为什么增量不适用 |
|---|---|
| 删除 POI | `03b` 会 `RAISE EXCEPTION` 拦截（行数变少即报错） |
| 修改 POI 坐标 | `gid` 不变，检测不到 → **静默漏算**，最容易踩 |
| `TRUNCATE` / 整表重灌 | `gid` 序列可能重启，检测失效 |
| 修改 `admin_area` | 格子本身要重建：先 `02` 再 `03` |

`03`（全量）跑完会同步刷新 `grid_500m_refresh_state`，所以两个脚本可以放心交替使用。

## 这张表在设计上要回答什么

**一行 = 一个 500 m 方格，但它统计的不是「格子里有什么」，而是「站在这个格子的中心，走 800 m 能到几个设施」。**

```
格子边长 500 m  ── 决定图上色块有多细（视觉分辨率）
统计半径 800 m  ── 决定数字意味着什么（步行 10 分钟）
```

两者**故意不相等**。若强求「内切圆」（500 m 格 → 250 m 半径），分析尺度会退到步行 3 分钟，
那个尺度下几乎处处达标，热力图没有区分度。推导见 `FE/docs/roadmap.md` §2.4.9。

一个 POI 会被约 **9.34** 个相邻格子的圆覆盖（实测 149,524 对 ÷ 16,016）。相邻格数值接近是**正确的**——
它说明可达性在空间上是连续的，不是 bug。

## 为什么是预计算，不是实时算

实时算一次要 39,820 格 × 16,016 POI ≈ **6.4 亿次球面距离计算**，单请求几十秒，不可行。

所以物化成表，改数据后跑 `03` 刷新。**代价是数据快照会过期**：

| 变更 | 需要做什么 |
|---|---|
| POI 增删改 | 跑 `03`（5–15 min） |
| `admin_area` 变化 | `TRUNCATE grid_500m` → 跑 `02` → 跑 `03` |

### 为什么不用触发器

ETL 批量导入 16,016 条会触发 16,016 次，每次更新约 9.34 格 → **149,524 次无用 UPDATE**，
导入时间从秒级变十分钟级。

**触发器适合少量离散写入，不适合批量导入。** 若将来数据变成持续增量写入，
再重构成 `poi × 格` 明细表 + 物化视图（那时刷新只涉及新增的 9 行）。

## 数据边界（必须写进 README 与图例）

13 个区的 POI 数几乎都在 **1,100–2,000** 之间（汉南 203、青山 574 除外），而面积比最高达 **79 倍**
（江汉 28.5 km² vs 黄陂 2,247 km²）。

→ **ETL 是按「每区抓 N 条」采的，不是按真实密度。**

所以热力图本质是「**高德 POI 采集分布图**」，不是「公共服务设施真实分布图」。
这句话要主动写出来,不要等被问。

## 常见错误

| 错误 | 现象 | 原因 |
|---|---|---|
| `ST_SquareGrid(500, ...)` | 只生成个位数格子 | `size` 单位是**度**，4326 下不能写米 |
| 忘了建 `centroid` 索引 | `03` 跑 30 分钟以上 | `ST_DWithin` 退化成全表扫 |
| `03` 第 1 步置 0 被删掉 | 26,786 个格子是 NULL | 第 2 步用 `JOIN`，空格不出现 |
| 分母写死成当前值 | 补采数据后 `avg(r)` 偏离 1.00 | 分母必须每次重算 |
| 密度分母用 0.25 km²（格面积） | 密度虚高约 8 倍 | 分子是圆内的，分母必须用圆面积 2.0106 |
